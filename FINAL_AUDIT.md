# SentinelAI final security and readiness audit

Audit of local `main` at `c79c7f5` and the uncommitted fixes described below. Test traffic used loopback, reserved example domains as strings and controlled browser fixtures. The audit used a pre-existing modified local history database only to make and verify a backup and count legacy records without displaying them.

## Executive summary

**Ready for a controlled, offline-first hackathon demonstration.** The React preview, Chrome URL and email screening, Gmail compose redaction, local privacy engine, history and threat-review API ran on the audited build. The 16-category demonstration email redacted and restored correctly. The hardened build keeps the same UI and compose animations. The webpage evidence endpoint worked with synthetic observations, while the production extension lacks an arbitrary-tab observer.

The biggest risks for distribution are historical private data and signing material, the trust placed in local API callers, and weak email recall. Treat scores as screening indices and discuss the evidence in each demo. A controlled demo and a production assessment require different evidence. [Demo instructions](DEMO_GUIDE.md)

## Backend security

`backend/server.py` binds IPv4 loopback. It checks a narrowly formatted Host and checks browser Origin. A known extension ID and local preview origins are accepted. Gmail is scoped to legacy email POST and its preflight, with a reduced response and threat collection disabled. Browser cross-site GETs without an Origin are denied when fetch metadata marks them cross-site. The service also accepts same-machine native requests without Origin so the command-line demo works. CORS is a browser boundary and local processes remain in the trust boundary.

| Route family | Inputs and storage |
|---|---|
| Health and history | Health resolves the two local artifacts. History filters type, offset and limit and returns metadata. Error bodies use fixed messages. |
| Scan URL/email, legacy and v2 | JSON with bounded body, text, HTML, header and list fields. Preview has no history write for trusted clients. The Gmail legacy endpoint returns a small response. Email v2 can return excerpts and detected values for the supplied input, so its responses belong in the same trusted local client context. |
| Privacy | A bounded 40,000-character field, validated country code and bounded finding IDs. Findings-only mode omits draft content except masked suffix metadata. Explicit redaction returns original-derived output to the caller. Audits store counts. |
| Page | Schema-checked integer observations and a parsed HTTP(S) address. Input HTML is not fetched. |
| Settings and threat review/export/prune | Validated setting keys and values, review actions, filters and numeric IDs. Current threat export can grow with approved rows. |

The body limit is 512 KiB. Socket I/O times out after five seconds. The service uses a 32-slot pending connection queue, without a global worker cap or total wall-time budget. JSON parse errors and storage failures produce generic messages. Dynamic SQL values are parameterized. Application logs suppress request body, target and header logging. The URL scorer performs no HTTP requests to inspected destinations. Public suffix data is bundled. The optional writing request is only to a locally configured loopback port, disables proxies and redirects, and caps responses at 128 KiB. The legacy `webpage_extractor.py` can fetch URLs when explicitly used as a script and is outside API dispatch. Leave it out of production routing. Model loads resolve fixed paths under `models/`. Only use trusted Joblib artifacts, since they use pickle.

## Chrome extension and OAuth

MV3 runs the Gmail content script in the normal extension isolated world. There is no externally connectable page message relay. Compose worker messages require the extension sender, Gmail URL and top frame. Toolbar icon changes require the popup sender and an allowed icon name. The default MV3 extension-page CSP applies. The bundle contains packaged scripts and assets. Gmail content is treated as untrusted. The overlay displays fixed markup and protects variable text, numeric and severity slots. Popup React strings use ordinary React text binding.

Manifest permissions remaining are storage, activeTab, contextMenus and identity. The URL popup uses activeTab. Context-menu registration remains, but no click listener was found in the active worker. The toolbar icon can reflect theme settings. The Gmail privacy count badge and inbox status badges are evidence UI. No code requests browser notification permissions or changes a site’s notifications. Separate access to the Gmail API, People API and Google revocation endpoint is for existing authorized sign-in flows. Gmail scopes are read-only mail plus basic profile. No Gmail send, delete or label mutation appears in the active code. The only draft edits are local DOM changes triggered by a click.

Chrome Identity owns token acquisition/cache. The popup keeps the current access token in React state and persists only a session preference. It fetches the current profile when restoring a session and resets inbox state when switching profiles. The list and detail fetches report 401 and clear the Chrome cached token before reauthentication. Sign-out clears local state before best-effort server revocation. Gmail message detail uses read-only `format=full`, skips attachments in body extraction, prefers MIME plain text and falls back to HTML-derived text or the snippet. There is no signature-based sender authentication result. Message details and HTML parsing remain bounded unevenly at the browser network layer. Manually check two accounts, logout/re-authentication and current extension-ID registration with a consenting test account. [Google token revocation documentation](https://developers.google.com/identity/protocols/oauth2/web-server)

## Privacy and address audit

The active Python detector is shared by the API, Privacy tab and Chrome compose. The test set covers email, Indian and international phones, Aadhaar, residential/mailing address, Indian and international postal codes, SSN, bank account, IFSC, IBAN, card, PAN, passport, UPI, passwords, API keys and auth tokens. `phonenumbers` validates regional number patterns. Aadhaar validates format and Verhoeff. Table-driven tests exercise wrong checksums and fallback boundaries. Card and IBAN checks use Luhn and python-stdnum validation respectively. PAN, IFSC, passport and bank patterns validate field shape and context. They do not check live registries. The audit includes order, tracking, invoice, transaction, date, ordinary quantity and arithmetic cases. Password discussion without an exposed value does not produce a secret redaction.

Address parsing matches local components in the original span. It starts with locators such as unit, house, numbered street, locality or box plus corroborating evidence, while the US prefilters can invoke the local usaddress CRF. A label, house number, street, city, state or postcode is optional depending on the other evidence. Indian flats/plots/colonies, landmarks, UK and Canadian postcodes, US mail examples, multiline blocks and in-sentence addresses are covered. Commas, numbers and linking words define boundaries. Some uncommon, unpunctuated, local-script or prefix-style addresses can be partial or missed. A bare location or generic landmark stays available in ordinary text. The presentation guide has 15 single-line examples, one five-line example and review examples. [Verified address and category guide](docs/privacy-demo.md)

In Chrome, selection defaults to high confidence. Review items are opt-in even for **Redact all**. The worker returns positions and masked findings to the preview. Per-editor state protects overlapping windows. Before applying edits the script compares the current snapshot, converts code point positions to UTF-16 offsets and updates only affected text nodes. Quotes and signatures are excluded by default. Undo checks that its nodes still contain the expected edited content. The audit records counts without private draft text. Formatted synthetic content and the full presentation email were verified through the installed worker. Real forwarded Gmail DOM variants remain manual.

## Email model and calibration

`email_phishing_model.joblib` is the deployed `email-tfidf-v1` body model. The training script uses lowercased word unigram and bigram TF–IDF (up to 20,000 features) and logistic regression. The loaded vocabulary contains 20,000 features. Classes are 0 legitimate and 1 phishing. The raw-model observation flags class 1 above 0.50. The original script exact-deduplicates the main email CSV and makes a stratified random 80/20 split. It cleans another labelled parquet but fits this pipeline on the first CSV. The raw datasets and exact row counts after cleaning were unavailable for this audit. Source overlap, duplicate templates across splits, provenance of specific labels, corpus imbalance and campaign leakage remain unresolved. The split method allows related templates in both partitions.

The earlier offline comparison fitted candidates on 2,042 legitimate and 629 phishing messages and validated on 1,388 legitimate and 319 phishing messages, using separate SpamAssassin and Nazario archives with exact/near-template screening. The 175-example labelled PhishFuzzer benchmark results below are archived measurements on the same deployed artifact, not a new evaluation run. Original source data were no longer present at their previous temporary locations. Brier score is a mean squared error for raw probabilities and does not establish calibration.

## URL model and calibration

`url_context_candidate.joblib` is the deployed 150-iteration histogram gradient-boosting artifact with 12 ordered features and an advisory threshold above 0.50. It is byte-identical to the archived evaluated candidate, uses its saved feature order and maps class 1 to phishing. Feature extraction normalizes host/root path and uses shape, URL length, IP, subdomains, digit and letter counts, HTTPS as one feature, path depth/encoding and hostname indicators. Query values are excluded from the candidate. Transport alone never establishes a safe verdict. No domain allowlist overrides the score. The legacy models use the historical reverse mapping where documented, with the deployed service no longer relying on the original forest. Earlier recomputation differed from published columns on URL length (about 20.6% agreement on the full dataset) and letters (0%); older samples reported a lower URL-length rate. This is evidence of feature mismatch, alongside domain shift and the observed false positives.

## Risk score and webpage evidence

The percentage shown in the existing interface is a complementary screening index. Evidence categories contribute their strongest marker and combine as one minus the product of remaining risk fractions. Evidence-confirmed findings set a strength floor. The model contributes a bounded fraction of remaining risk (weight 0.25 for email and 0.70 for URL). Link observations contribute at a discount. Grammar contributes up to six percentage points of remaining evidence only when the independent evidence reaches the minimum. Privacy counts do not contribute. When scored, risk and displayed safety add to 100. Sparse text or a missing model produces an unscored result unless independent evidence supports a warning, in which case the warning still explains model availability. A URL model flag alone can produce caution. Presentation materials must label the percentage as a heuristic/model index, separate from raw class probability or calibrated safety.

The page endpoint receives bounded numeric observations for links, frames, form structure and behavior. The shipped extension does not implement a general page collector for visible text, title, hyperlink extraction, form events, full-screen changes, navigation or notification state. The controlled browser fixture changes a page after load and passes only synthetic observations, ignoring the synthetic password value. Backend fixture outcomes were zero alarms in four benign cases (cookie banner, newsletter, same-host login and ordinary notification request) and three detections in three suspicious cases (support scare, prize/payment and blocking impersonation). Those rates apply only to the fixtures. The existing Gmail observer scans mail cards and drafts, not other sites.

## SQLite and threat review

Application tables cover scan history, preferences, trusted-domain metadata and privacy audits. The migration changes a legacy non-null confidence column transactionally and keeps existing rows. New history writes contain assessment metadata, marker IDs and numerical score only. The separate threat database uses foreign keys, secure deletion, transactions and a five-second lock timeout. Both paths can create their parent directories. Sixteen parallel audit writes passed on a disposable DB with the expected totals. An injected storage failure returned a generic response. The CLI uses a private file umask. The working history DB existed before the audit and retains legacy data.

Threat collection requires a global opt-in and explicit per-scan consent. Numeric fields are bounded and deduplicated by normalized fingerprints. A separate text policy can store allowlisted terms, with URLs and detected private spans excluded. Predictions populate assessment only. A person assigns and confirms the label before approval. Relabelling invalidates approval. Prune uses user retention settings when invoked. There is deletion of individual threat rows and no scheduled prune by default. Export selects approved rows only. The candidate training CLI rejects non-approved rows, conflicting labels and shared split groups and writes separate candidate artifacts. Existing unit tests cover numeric and masked-text pathways. Fingerprints of small feature sets can merge unrelated examples with identical features. Keep ground-truth review independent.

## Repository and credentials

The scan read 188 accessible non-vendored text blobs with common credential patterns and counted fields from historical SQLite snapshots in memory. It confirmed the private signing key. The public manifest key and Google OAuth client ID are identifiers used for the authorized extension. The scan did not find another high-confidence credential pattern. It cannot rule out secrets in untested formats, deleted hosted refs, archives or copies held by others.

The local backup `.runtime/backups/repository-cleanup-20261125-133615/sentinel_ai.db` passed SQLite integrity checking and contained 585 history rows. The live file bytes matched the before-audit hash. The default threat store did not exist at backup time. Both runtime paths and sidecars are ignored. The scan DB and signing key are staged to leave Git while their local files stay available with owner-only permissions. Old commits and stashes still retain sensitive material. The repository also still tracks a copied virtual environment, generated extension output and 1,528 vendored npm paths. Avoid staging those generated files when rebuilding, and handle index cleanup separately from any coordinated history remediation.

If the repository was shared, treat the old signing material as exposed. Determine which package and OAuth registrations rely on it, then coordinate replacement builds, registration updates and revocation with the owners. Review who could access historical private previews and arrange any necessary notification and restricted backups. A coordinated history cleanup and hosted-cache review needs explicit authorization and cannot recover copies already held by others. Back up each teammate’s database before pulling a change that removes the tracked file, then restore the copy to an ignored path and set `SENTINELAI_DB_PATH`. No registration, key or historical record was changed.
